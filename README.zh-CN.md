# StashBar

[English](README.md) | [简体中文](README.zh-CN.md)

给刘海屏 MacBook 用的菜单栏"抽屉"小工具——把不常点、但要一直运行的菜单栏图标先收起来，
需要用的时候再点开。

就像我的世界里的箱子：扔进去的东西还在运行，只是暂时看不见，打开箱子就能拿。抽屉是**向下**
展开的（不会横向展开），不会再去抢占本就紧张的横向菜单栏空间。

🗃 抽屉图标常驻在菜单栏里；它左边紧邻的一段区域就是"收纳区"，被一条和菜单栏材质融为
一体的条带盖住：

![StashBar 的抽屉图标和收纳区](docs/closed.png)

## 问题

带刘海的 MacBook（14/16 寸 MacBook Pro）菜单栏可用宽度很窄。只在菜单栏常驻图标的
App（Cloudflare WARP、Dropbox、VPN 客户端、剪贴板管理器……）很容易被刘海挡住或挤出
屏幕之外。常见的解决办法是先退出这个 App 腾地方，用的时候再重新打开——很烦。

## StashBar 做什么

StashBar 在菜单栏加一个小抽屉图标（🗃）。它左边的一段区域就是"暂存区"：按住 ⌘
把任意菜单栏图标拖到这段区域里（和系统自带的菜单栏图标排序手势一样）。StashBar 会
用一块和菜单栏本身材质一致的遮罩盖住它——图标看起来被收起来了，它背后的 App 完全
不受影响，继续正常运行。

- **点一下抽屉** → 从图标下方展开一个真正的面板（向下展开、锚定在图标下方），列出
  当前暂存的每一个 App，并附带它图标的实时缩略图。
- **点某一项** → StashBar 会替你点击那个图标在真实屏幕上的位置，然后关闭面板——
  效果和你亲自点它一样，只是平时不占菜单栏空间。
- **右键抽屉图标** → 调整暂存区宽度、开机自启动、授予辅助功能权限。

不会删除任何图标，不会杀掉任何进程。StashBar 从不移动、缩放或修改其他 App 的状态栏
图标本身——它只决定菜单栏某一段区域此刻是否被遮罩盖住，以及是否要替你转发一次点击。

## 安装

需要 macOS 14 及以上，以及 Xcode 命令行工具（PATH 里要有 `swift`）。

当前源码版本：`v2.0.2`。版本记录见 [CHANGELOG.md](CHANGELOG.md)。

```bash
git clone https://github.com/zhuhroscar-tech/stashbar.git
cd stashbar
make install
```

这会编译 release 版本、打包成 `StashBar.app`、签名、安装到
`/Applications/StashBar.app` 并启动它。菜单栏图标会立刻出现。

因为没有做 Apple 公证，从 Finder 直接双击首次打开可能会提示"无法验证开发者"——按
上面的方式从终端运行 `make install` 就不会触发同样的拦截；如果还是被拦，在 Finder
里右键这个 App → 打开，允许一次即可。

如果登录钥匙串里已经有名为 `StashBar Local Dev` 的本地签名身份，打包脚本会使用它，
这样每次改代码重新编译后，下面提到的辅助功能/屏幕录制授权都不会失效。若没有这个身份，
脚本会退回到 ad-hoc 签名，macOS 可能会在重建后再次要求授权。

## 使用方法

1. 按住 **⌘** 把某个菜单栏图标拖到 🗃 抽屉图标的**左边**。它就被收起来了——看不见，
   但背后的 App 仍在运行。
2. **点击** 🗃 ——图标下方会展开一个面板，列出所有暂存的 App 及其实时图标缩略图。
3. **点某一项**来操作它——StashBar 会替你点击那个 App 真实的图标，然后关闭面板。
4. 点面板以外的任何地方也会直接关闭面板，不会触发任何操作。

右键 🗃 可以设置：
- **加宽 / 缩窄暂存区** —— 多宽的一段菜单栏区域算作"抽屉范围"。
- **开机自启动**。
- **授予辅助功能权限…** —— 替你点击暂存图标需要这个权限（见下）；没有这个权限时
  StashBar 依然会显示每个暂存图标的实时缩略图，只是无法替你点击。

## 原理

两套完全基于公开 API 的独立机制：

**识别暂存了什么。** 其他 App 的菜单栏图标本质上是固定 CoreGraphics 窗口层级
（`kCGStatusWindowLevel`，即 25 层）上的真实屏幕窗口。StashBar 读取公开的
`CGWindowList` API，查找当前位置落在暂存区内的这类窗口——不使用任何私有 API，
也不轮询其他进程的内部状态。

**展示暂存了什么。** 每个暂存图标的实时像素通过 `ScreenCaptureKit` 的
`SCScreenshotManager` 抓取，精确限定在那一个窗口上，所以面板里显示的永远是
*当前真实*的图标（比如带徽章、带动画的状态），而不是一张缓存的旧截图。

**替你点击。** 在当前 macOS 上，单纯把合成点击事件 post 给另一个进程的 PID 并不
可靠——事件还需要在几个未公开的 `CGEventField` 字段里带上目标窗口的 ID，这个方案
与开源菜单栏管理工具 [Ice](https://github.com/jordanbaird/Ice) 自身的
`MenuBarItemManager.click(item:)` 实现做了交叉验证。这一步需要辅助功能权限——
和任何向其他进程发送合成输入事件的 App 一样；没有这个权限时 StashBar 只在面板里
显示一条可关闭的提示，其余功能（检测、缩略图展示）照常可用。

**面板本身**是一个无边框 `NSPanel`，每次打开都会重新计算它的 frame：无论当前展示
几项，左上角锚点位置永远不变，只有高度会变，宽度永远不变——具体不变式见
`Tests/StashBarTests/DrawerPanelLayoutTests.swift` 里的
`panelGrowsDownwardNotSideways` 测试。

## 测试

```bash
make test    # 纯逻辑单元测试：暂存区判定、面板尺寸计算、事件字段
make check   # 测试 + release 编译
```

测试套件（`swift-testing`，无需安装 Xcode）覆盖了过去必须手动操作真实菜单栏才能
验证的部分：哪些图标算作"在暂存区内"（`StashScannerTests`）、面板的 frame 计算
是否真的只向下展开、绝不会横向或向左偏移（`DrawerPanelLayoutTests`），以及合成
点击事件是否携带了正确的目标进程/窗口字段（`ClickForwarderTests`）。全程不涉及
任何真实窗口、真实屏幕，也不会控制你的鼠标。
